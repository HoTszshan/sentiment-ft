# 实验报告：协议 token 解冻与开口播种的 A/B 验证

**日期**：2026-10-24
**基座**：Qwen3-4B-Instruct-2507（non-thinking，`tie_word_embeddings=True`）
**数据**：训练 73 条（纯领域，已剔除 9 条异格式 anchor），验证 8 条
**训练**：POC1，LoRA r=16 / alpha=32（7 个线性层），lr 1e-4，cosine，batch 2 × 累积 4，6 epoch = 60 步
**评测**：`evaluate_sft.py` 模式 B（金标 vs 预测），发布门 4 项

---

## 1. 实验目的

验证两个候选修复中，**哪一个才是「模型学不会输出格式」的真正原因**。

要回答三个问题：

1. **协议 token 解冻是不是决定性变量？** 即：给 `<think>`/`</think>` 两行 embedding 挂可训练偏移，是否是格式学会的**必要条件**。
2. **前缀预置还有必要吗？** 即：把 `<think>\n` 直接写进 prompt 前缀，在已有 token 解冻的前提下是否还带来收益。
3. **格式学会之后，内容指标能否同步达标？** 如果不能，瓶颈在哪一层。

---

## 2. 方案设计

三组配置，**只在这两个开关上不同**，其余超参与数据完全一致。

| 组 | 名称 | 前缀预置 | token 解冻 | 作用 |
|---|---|---|---|---|
| **A** | 默认配置 | 关 | 开 `[151667, 151668]` | 待验证的主方案 |
| **B** | 对照 A | 关 | **关** | 验证 token 解冻是否关键变量；关掉后回到「模型必须自己挑 token」的原始状态 |
| **C** | 对照 B | **开** | 开 | 验证前缀预置作为兜底方案：起始标签由前缀提供时是否还有额外收益 |

### 两个开关的技术含义

**token 解冻**：`LoraConfig(trainable_token_indices=[151667, 151668])`
给这两个 token id 的 embedding 行挂一个 `(2, 2560)` 的可训练偏移量。因为 `tie_word_embeddings=True`，这同一个参数同时决定输入表征与输出 logits，所以一处训练、两端生效。落盘只增加约 10 KB。

**前缀预置**：把 `<think>\n` 拼进 assistant 前缀。训练侧它落在掩码区（不计 loss），推理侧它落在生成前缀里（不占生成预算）。效果是模型不用学「第一个词吐什么」。

### 为什么需要这两组对照

此前诊断发现：`<think>`/`</think>` 的 embedding 行范数只有 0.367（普通词中位数 1.106），且与 `</tool_call>` 余弦相似度 0.92~0.99 —— 这两行从没被训练过，而 LoRA 只改 attention/MLP，默认无法触及它们。由此产生两个候选修法，必须分离验证。

## 4. 发现与结论

### 4.1 token 解冻是决定性变量，且是必要条件

**关闭 token 解冻，格式完全学不会**：`p(</think>)` 60 步后仍是 0.001，`greedy_ok` 全程 0/3，8 条预测全部以 `</tool_call>` 开头。

**开启 token 解冻，20 步内开始起效，40 步完全学会**：`p(</think>)` 从 0.015 涨到 0.779，`greedy_ok` 从 0/3 到 3/3。

这证明此前的诊断成立：**不是训练步数不够，是输出行被冻结导致模型在 logits 层面无法区分 `</think>` 与 `</tool_call>`**。给这 2 行加 10 KB 偏移，就能解开。

> 附带结论：B 组的 train_loss（1.019）并不比 A 组（0.975）差多少，但 loss 只掉了 4%，格式却从 100% 变成 0%。**loss 曲线不能用来判断格式是否学会**——这也是必须保留 canary 的原因。

### 4.2 前缀预置：无额外收益，可以去掉

A 与 C 的格式指标完全一致（都是 100%），`p(</think>)` 曲线几乎重合（0.015 vs 0.008 → 0.829 vs 0.819），`greedy_ok` 都是 40 步后 3/3。

**结论：有了 token 解冻，模型 40 步内自己学会吐 `<think>`，不需要前缀预置。**

去掉前缀预置还有三个额外好处：

1. **adapter 自包含**：播种把协议塞进了推理代码。换客户端（vLLM / 第三方）时忘了加 flag，格式立刻崩。不播种就没有这个隐性依赖。
2. **梯度更纯**（实测）：不播种时 `<think>` 只出现在监督目标，delta 梯度范数 **6.26**；播种时它同时作为输入 token，梯度降到 **3.78**（tie 权重承担双重角色，两侧拉扯）。
3. **锚点兼容**：若重新引入异格式 anchor（output 无 `<think>`），播种会造出「prompt 塞了 `<think>` 但金标直接是 JSON」的畸形监督 —— 教模型「开口后不用闭合」。

### 4.3 格式解决后，瓶颈转移到 irony / service

A 和 C 的 sentiment Macro-F1 已达 90.48%，但：

- **irony 召回 0/1**，直接卡死 gate2；
- **service 召回 0/1**（risk 的 per-key 诊断线）；
- risk Subset Acc 87.5%，差门槛 2.5 个百分点。

**这是数据量问题，不是机制问题**：训练集 73 条里 irony 只有 8 条，验证集 8 条里 irony 只有 1 条。单条样本就能让召回率在 0% 和 100% 之间跳变，当前数值没有统计意义。

### 4.4 一个必须记录的评测 BUG

B 组的 `gate2: PASS` 是**空判定，不是真实通过**。

`release_gate.py` 的逻辑是：若某安全字段在本次金标上无支撑样本（`cur_v is None`），跳过该字段并记为 "skipped"。B 组因 JSON 全部解析失败、没有任何有效预测，`irony_recall` 为 `None`，于是被跳过；其余安全字段也全部跳过，`gate2_ok` 保持初始值 `True`。

**含义：格式全崩的模型反而拿到 gate2 PASS。** 这是门禁逻辑的缺陷（应把「全部字段被跳过」判为 N/A 或 FAIL，而不是 PASS），但本次实验未修改它，只做记录。

### 4.5 A 与 C 的内容差异属于噪声

- hard_case Macro-F1：A 43.33% vs C 40.00%（差 1 条样本）
- risk Subset Acc：A 87.50% vs C 75.00%（差 1 条样本）

验证集仅 8 条，**这两个差值不作为前缀预置优劣的证据**，也不建议基于此排序两组。

### 4.6 结论与建议

**结论：保留 token 解冻，去掉前缀预置。默认配置（A 组）即为最终方案。**

后续按优先级：

| 优先级 | 事项 | 理由 |
|---|---|---|
| **P0** | 扩充 irony / service 样本，验证集扩到 ≥40 条 | 当前 irony 召回 0%，且 8 条验证集使所有内容指标不可判定 |
| **P1** | 修 `release_gate` 的 gate2 空判定 | 格式全崩的模型拿到了 PASS，门禁存在假阴性 |
| **P2** | 跑 POC2 / POC3 消融 | 格式基线已干净，可验证骨架掩码、字段加权是否提升 F1 |
| **P3** | 协议标签改名（`<|begin_of_thought|>` 等） | 仅在换基座或需与原生 thinking 共存时再做。实测代价：adapter 132 MB → 1607 MB，需改 19 个文件 / 82 处字面量 |

### 4.7 关于 canary 的成本

本实验依赖 canary 才能在第 20 步就判定格式是否可学。代价是训练变慢：带 canary 60 步约 740 s，不含 canary 约 220 s（按 33 步 121.6 s 线性折算，非实测）。

已从「每 10 步 × 8 条 × 512 token」降到「每 20 步 × 3 条 × 400 token」，耗时从 2210 s 降到 747 s。仍约 3 倍于无 canary 训练，建议正式轮设为 `--canary_every 30` 或直接关闭。

## 附录 B · 已评估但暂不实施的方案

记录在此是为了避免重复论证。**这些不是待办**，需要重新评估后才进入落地清单。

### B1 · 协议标签改名（`<|begin_of_thought|>` / `<|end_of_thought|>`）

**收益**：跨基座可移植性。现在借用的 `<think>` / `</think>` 是 Qwen 词表里的原生 token，
换基座时协议含义会漂移；自带 special token 的协议更干净，也能与基座原生 thinking 模式共存。

**实测代价**：

| 项目 | 数值 |
|---|---|
| adapter 体积 | **132 MB → 1607 MB** |
| 原因 | `resize_token_embeddings` 后 peft 判定「词表变了」，把整张 embedding 表塞进 adapter：`base_layer.weight (151671, 2560)` × 2 份 |
| 新 token 行初始范数 | 0.371 —— 仍是同一共线簇里的随机行，不天然「更可分」 |
| tokenizer 依赖 | 必须随 adapter 分发，否则下游 token id 全部错位 |
| 代码改动面 | 19 个文件 / 82 处 `think>` 字面量 |

**结论**：POC 阶段不实施。当前问题已被 10 KB 的 delta 解决，不值得为已修好的问题动 19 个文件。
